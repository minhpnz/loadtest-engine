# Self-service ephemeral load testing — writeup

## 1. Context I assumed, and why

- **AWS, GitHub, ~50 services.** The services are assumed to run on AWS with code on GitHub. EKS provides quota, NetworkPolicy and admission; GitHub Actions is already familiar. For one platform team and ~50 services, a shared cluster with a namespace per run is cheaper to operate than clusters per team.
- **Network.** A dedicated non-production cluster in `ap-southeast-1`, in an existing VPC passed by ID; this stack never changes networking.
- **Ownership.** Developers own *what* is tested (allow-listed GET endpoints, thresholds); the platform owns *how hard* and *where* (VUs, duration, resources, target host, identity, teardown). Without tickets, this split is the guardrail.
- **Target and dependencies.** One service instance per run, by image digest, synthetic data, egress denied; production and staging cannot be targeted. Next: per-run stubs (e.g. WireMock) and a seeded database inside the run namespace, covered by the same quota and teardown. Shared staging is rejected: data risk, noisy results.
- **Scale.** One profile (10 VUs for 30 s including a 5 s ramp; smoke is 1 VU for 10 s; target capped at 250m CPU / 128 MiB) and one run at a time.

**Developer journey:**
1. Add `load-tests/load-test-config.yaml` (one-time catalog PR per new service).
2. Push to `main`, or press **Run workflow** and pick a commit.
3. CI builds or reuses the image; on push, a reviewer approves.
4. ~2.5 min later, read the verdict in the job summary; open `load.html`.
5. Nothing to tear down.

**Real runs on EKS, 22 October 2026** (the cluster was destroyed afterwards):

| Run | Change | Result |
|---|---|---|
| Scenario 1: Run workflow | healthy code | **PASS**: p95 209.9 ms (< 250), 0 % errors, 1,366 requests, 45.2 req/s; load-test job took 2 min 32 s |
| Scenario 2: push, then approval | buffer raised from 1 to 32 MiB per worker | target **OOMKilled** twice (exit 137) under 10 VUs; workflow red; cleanup complete |

Same configuration hash, different image digest. Scenario 2 was recorded as `ABORTED`: the dead container's CPU series went stale and the safety monitor stopped first. Fixed in `e63c52b`: an observed `OOMKilled` now yields `FAIL` even when a safety abort stopped the stage.

These numbers are a **regression signal under a fixed load shape, not a capacity figure**: generator and target share a Spot-backed cluster and the target has a small fixed limit. Compare runs of the same service, not production traffic.

## 2. Major decisions and the alternatives

| Decision | Picked | Considered | Why |
|---|---|---|---|
| Environment | Shared EKS, namespace per run | Terraform cluster per test; ECS/Fargate task | A namespace is ready in seconds; a cluster takes on the order of half an hour, for a 40 s test, and needs near-admin IAM in CI. ECS loses quota, NetworkPolicy and admission. |
| Load generator | k6 Job per stage, script generated by the platform | Locust; JMeter; k6 Operator | Thresholds give a pass/fail, native HTML export, Prometheus remote-write for live safety checks. No developer JavaScript runs. The Operator only helps beyond one pod's capacity. |
| IaC layout | Terraform `infra/modules/` (EKS, OIDC role, results bucket) + `infra/live/nonprod-apse1/` | One flat root; Terragrunt; add-ons as `helm_release` | Modules are reused by the next environment without copying; Terragrunt is overkill for one environment. Add-ons belong in GitOps, not Terraform state. |
| Developer interface | YAML in the service repo + two GitHub workflows | Web portal; Kubernetes CRD + operator; a test on every PR | No new UI or credentials. The approval gate stops a push from spending money unintentionally. Images are tagged by git tree hash, so nobody types a digest. |

**Supporting choices.** CI runs on one persistent runner Deployment in EKS: the engine needs the private API, guard and Prometheus, and the cluster is destroyed as a whole at decommission, so per-run runner registration buys nothing. Allow-listing GitHub-hosted runner IPs per run was rejected: it needs `eks:UpdateClusterConfig`, which cannot be scoped to CIDRs. Images are public on GHCR (free, no pull secret; ECR for private code). Terraform is applied from an admin machine because it creates CI's own OIDC role. Results go to the job summary, a downloadable artifact (k6 HTML, `report.json`, logs) and an expiring encrypted S3 bucket.

## 3. Trade-offs I accepted

**Cost.**
- Two on-demand t3.medium nodes, one Spot node, EKS, monitoring and public IPv4 bill while the cluster exists. I did not compute a monthly figure: spend is bounded by node count and by destroying the cluster, not by dollars.
- No autoscaler, no on-demand fallback for Spot; the AWS Budget has no recipients in the demo.
- The demo is applied and destroyed per session (58 resources); the results bucket must be emptied first, by design.

**Complexity.** A 927-line Python engine shells out to `kubectl` and keeps its state in a ConfigMap slot. It is simple to audit, but it does not reconcile: if the runner dies, the one-minute reaper and the Job deadlines clean up instead.

**Blast radius.**
- Namespace isolation is not a VM boundary. Each run gets a ResourceQuota, LimitRange, default-deny NetworkPolicy, restricted Pod Security, no service-account token and an Istio authorization policy.
- Admission policies fix the generator image, VU and duration ceilings and Spot placement, and confine the CI identity to `loadtest-*` namespaces.
- The stage aborts when target CPU exceeds 90 % or errors exceed 5 % for 30 s, or when telemetry is missing.
- **Not yet exercised on EKS:** these controls were applied in both runs, but the deny paths (egress, cross-namespace calls), the Alertmanager stop path and External Secrets have not been tested there.
- **Terraform:** the cluster creator keeps cluster-admin, and a single state holds the cluster, IAM, bucket and budget. That is fine for a disposable cluster. For a shared one I would split state by layer and use named admin roles.

**Developer experience.**
- GET only, one generator, one profile, no authenticated journeys.
- One global slot: a run holds it for about 2.5 minutes, so about 20 runs an hour. That is enough for on-demand use across 50 services, not for a test on every PR. Revisit when queue wait exceeds ~10 minutes.
- A failed cleanup keeps the slot locked on purpose.
- Onboarding is **one catalog PR per service, once**. Every test after that is ticket-free. Per-team folders with CODEOWNERS would remove the platform from that review.

**Security.**
- **CI identity.** The role trusts GitHub's immutable OIDC subject (`owner@id/repo@id`) for `main` and the `loadtest` environment, and can only describe the cluster and write results. The engine verifies run, workflow, event, commit and person; on push that is the **approver, not the pusher**.
- **Persistent runner.** The repository still uses GitHub's default fork policy (approval for first-time contributors only); it must be raised to *all outside collaborators* before wider use. Both workflows trigger only from `main`/`workflow_dispatch`; checkout cleans the workspace; each job gets fresh one-hour OIDC credentials. Residual risk, a maintainer merging a malicious workflow, is covered by branch protection on `.github/`; in a shared org, a runner group limits it to this repository. Revisit when the cluster becomes long-lived and shared.
- The image-to-commit link relies on tags anyone with push access could set; it is not yet backed by a signature. Terraform state is local; revisit at the second operator.
